Powered TAC USB bench: results

Tested 2026-10-11. The user confirmed the aircraft, ground radio and TAC bench was powered, TAC remained connected to laptop USB, and aircraft propellers were removed. The user reported 21.35 V on TAC's Drone Volts telemetry page. All hardware captures are finished; the user was told the aircraft could be powered down. Later physical power state is not assumed.

What the live test established

Check Observed result Meaning
USB descriptors Same device and HID descriptor hashes as the isolated baseline; 35b6:0004, HID + CDC ACM No new USB interface appeared with the powered link
HID 7 Linux axes, 16 buttons; 23 initialization events, zero changes in 3 seconds Existing gamepad interface remains available; no control mapping or movement requested
Receive-only CDC 231 bytes in 20.080 s: 11 valid HEARTBEAT frames, zero other messages Payload matches the controller-local heartbeat from the disconnected-radio test
Parameter-list query Complete response: 97 entries indexed 0..96, each declaring total count 96 Reproduces the static off-by-one discrepancy
Parameter origin All 97 names, raw four-byte values and type bytes exactly match the compiled v1.3.6 table at 0x6b254 This is TAC's compiled table, not evidence of the aircraft's current configuration
Capability query Twice: 44-byte AUTOPILOT_VERSION prefix with header declaring 60 payload bytes / 72 total frame bytes Truncated response cannot validate as a complete MAVLink packet
Capability source Function 0x5a6d0 serializes the response but explicitly passes 0x2c (44) to USB send Live truncation matches a concrete firmware implementation defect
Aircraft telemetry over USB No battery or position messages in the saved samples USB output is selective; TAC's on-screen 21.35 V reading is a separate user observation

The data does not prove telemetry freshness, a GPS fix, exact installed firmware release or physical aircraft configuration. In particular, TAC's local heartbeat and local parameters must not be treated as an independent flight-controller identification. The firmware's position-output path suppresses output when either stored coordinate is zero, so absence of GPS packets does not distinguish lack of fix from other missing data.

Saved sessions and scope

local-info-run2 26.062 s 2,126 4 heartbeat + 54 parameters 58

The first two parameter requests needed longer receive time; the final parameter-only run captured every entry, with the last arriving at 35.584 s. Variations in response cadence are observed, but their cause is not established.

A total of 130 application bytes were sent: two fixed COMMAND_LONG requests for command 512 with parameter 1 = 148, and three PARAM_REQUEST_LIST requests. Each targeted system 1 / component 1. No arm, control-output, home-setting, parameter-write or firmware-update request was sent. No Ethernet/MATRIX electrical probe was performed. USB CDC opening and closing can change DTR/RTS; these were host serial captures, not an electrically passive tap.

Capture interruption and decoder recovery

The first 30-second receive attempt was killed by REA's idle timeout before saving. It sent zero application bytes, but its original terminal settings were not persisted and restoration is unverified. The capture helper now saves a pre-change termios snapshot, flushes a start message, handles SIGTERM, and writes a result during cleanup. Successful captures used sufficient supervisor timeout and all four restored their own starting snapshots. This does not prove restoration to the state before the interrupted attempt.

The initial pymavlink streaming parser consumed parts of following heartbeats while trying to complete the truncated capability packet. The offline decoder was improved to advance one byte after a failed candidate. The *-recovered.json reports are authoritative for frame counts: both malformed responses leave exactly 44 unparsed bytes, and subsequent heartbeats are recovered with valid CRCs. Rejected-candidate spans can overlap valid frames; candidate counts are not physical line-error rates. Earlier decoder outputs are retained as historical evidence.

Repeatable tools

scripts/capture_serial_receive.py performs a bounded receive-only capture. It requires either --aircraft-unpowered or --powered-bench-props-removed, based on a fresh, applicable user setup confirmation. scripts/inspect_tac_ctrl.py reads descriptors and joystick state. scripts/query_tac_local_info.py sends only the two reviewed information-request forms; --parameter-list-only selects a single parameter request and a 45-second receive window. --dry-run prints and validates the packets without opening hardware.

The offline decoder uses pymavlink and the official common message definitions. Dependencies are isolated and pinned:

python3 -m venv .tools/usb-bench
.tools/usb-bench/bin/pip install -r evidence/usb/powered-bench/requirements.txt
.tools/usb-bench/bin/python scripts/decode_tac_mavlink.py evidence/usb/powered-bench/parameter-list-run3.json --out /tmp/orqa-parameters-new-decode.json

Choose a new output path; existing outputs are not overwritten. The offline checks cover agreement with the earlier independent heartbeat decoder, signed position fields, single-byte chunks, corrupted CRCs, truncation and recovery of the real malformed-capability captures.

Next boundary

The USB test is complete. Raw Ghost validation still requires a suitable differential receive connection to the documented MATRIX UART pairs. The laptop Ethernet port does not implement that interface. No new hardware connection is requested by this report.
