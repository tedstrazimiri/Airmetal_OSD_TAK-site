Offline Ghost traffic decoder

scripts/decode_ghost_traffic.py decodes saved UART bytes using the framing recovered from TAC.Ctrl v1.3.6. It uses Python 3's standard library, reads regular files only, and never opens USB/serial devices or network connections. Nothing is transmitted.

Run the included demonstration

From [local workstation]/Documents/ChatGPT/REA - Orqa GCS:

python3 scripts/decode_ghost_traffic.py examples/ghost-demo.capture.json --input-format json

The example is synthetic, not a hardware capture. It contains two separate streams, arbitrary read-chunk boundaries, two noise bytes, one deliberately damaged CRC and a GPS unsigned-coordinate boundary case. Expected result: 3 valid C2 frames, 8 valid telemetry frames, 1 CRC-rejected candidate and 16 unparsed C2 bytes. The intentionally implausible GPS values demonstrate a known interpretation limit.

Decode a saved capture

python3 scripts/decode_ghost_traffic.py capture.bin --out decoded.json

The default is raw binary. --input-format hex accepts contiguous or whitespace-separated hexadecimal with optional # comments. Addresses/offset columns, 0x prefixes and logic-analyzer CSV are deliberately not guessed; export raw bytes or convert explicitly. --input-format json accepts the chunk structure below. --direction controller_to_radio or radio_to_controller adds a capture label; conflicting address hints are reported.

The terminal shows a short frame preview; --show 30 changes its size. The JSON retains all accepted frames, raw payloads, field evidence, byte offsets, checksum-rejected candidates, unparsed byte ranges, source/stream SHA-256 values and any acquisition-chunk timestamps. --out is optional and refuses to replace an existing file. The parent output directory must exist.

Exit statuses: 0 = analysis completed; 1 = --strict was requested and there were no accepted frames, or there were unparsed bytes or rejected candidates; 2 = malformed input, I/O failure or a resource limit. Without --strict, damaged data is still a successful analysis, with diagnostics. No partial report is written on a decoder limit error.

Default report limits are 16 MiB of input, 100,000 accepted frames and 10,000 diagnostics across all streams. Large captures can be split, or these limits changed explicitly with --max-input-bytes, --max-frames and --max-diagnostics.

Captures with separate C2 and telemetry lanes

Keep the directions separate. UART byte streams must not be merged by interleaving bytes from the two pairs.

{
  "schema": "orqa.ghost.capture.v1",
  "capture_origin": "synthetic",
  "streams": [
    {
      "id": "c2",
      "direction": "controller_to_radio",
      "chunks": [
        {"at_ms": 0, "hex": "81 0c 10 23"},
        {"at_ms": 1, "hex": "61 45 89 c7 ab 18 7c e0 ff 15"}
      ]
    }
  ]
}

Add a second stream with id: "telemetry" and direction: "radio_to_controller" for the other pair. Chunk timestamps are optional, nonnegative milliseconds, in nondecreasing order within each stream. They describe capture chunks, not precise byte or RF arrival times. Each decoded frame records its first and last source chunk. Missing timing stays unknown.

For compatibility, a single top-level chunks array containing hex and optional at_ms is also accepted. This does not turn the older TAC USB MAVLink captures into Ghost traffic: those are different interfaces and protocols. Input origin is a declared label, not independently authenticated provenance.

What is decoded

Address/type Output Boundary
81/10, 81/11, 81/12 Channels 1–4 as raw 12-bit values, plus channels 5–8 / 9–12 / 13–16 as raw 8-bit values No physical stick assignment, pulse-width conversion or universal scaling
81/50 Staged home latitude/longitude, signed little-endian integers scaled by 10^7 Does not prove delivery or aircraft acceptance
80/23 Raw receiver fields; UI-equivalent voltage, current and consumed mAh Units/scaling traced to firmware; live values/freshness not validated
80/25 Raw receiver fields; firmware UI-equivalent unsigned coordinates and altitude Signed coordinate interpretation and altitude datum unresolved; out-of-range display values flagged
80/20, 80/26, 80/32, 80/33 Source-backed raw fields and byte order Unproven field names/units remain unassigned
80/21, 80/22, 80/24 Dispatch label and opaque payload Full payload interpretation not implemented
Unknown types and address 90 Raw payload and CRC result 90 is recognized by fragment assembly but not accepted by the traced TAC dispatcher

Meaning depends on both address and type. For example, an 80/10 packet is not silently interpreted as an 81/10 control packet. Known control/home layouts require exactly ten payload bytes. The traced receive callback accepts 14- and 27-byte total frames; other CRC-valid sizes are retained with a profile note and opaque payload.

The UI byte-order helpers were confirmed from instructions during this build. Type 23 effectively uses little-endian 16-bit wire values and divides volts/amps by 100. Type 25 effectively uses little-endian 32-bit coordinates, but the traced UI converts them unsigned. The decoder preserves that distinction rather than assuming valid signed geographic coordinates.

Framing and recovery

The frame is address | length | type | payload | CRC. Total bytes = length + 2. CRC-8 uses polynomial 0xD5, initial zero, no reflection and no final XOR; it covers type and payload only. Address and length are outside the checksum. CRC validity is not sender authentication or proof that a random candidate is genuine traffic.

The parser buffers incomplete frames across chunks. After a CRC failure or impossible length, it advances one byte and searches again. At EOF, it also scans past incomplete candidates so a bogus long length cannot hide a later complete frame. This is an analyst recovery policy, not an emulation of the firmware's limited fragment assembler. A checksum collision can remain ambiguous.

Accepted frame bytes and unparsed ranges partition the entire input stream. Rejected-candidate diagnostic spans can overlap later accepted frames; their counts must not be interpreted as measured packet loss or line-error rates. Every unknown payload remains available for later analysis.

Tests and evidence

python3 -m unittest discover -s tests -v

The tests use independently constructed literal frames whose CRCs were computed with polynomial long division, not the production checksum function. Coverage includes all three channel banks, nibble boundaries, mixed byte order, unsigned GPS limits, opaque packets, every split position in a mixed stream, single-bit corruption, noise, false lengths, chunk timing, resource bounds and exclusive output creation.

  • Literal synthetic fixtures
  • Firmware UART/framing analysis
  • Supplied MATRIX pinout and capture boundary

Hardware validation remains outstanding. The decoder is ready for saved traffic, but no real Ghost capture was used in this build. The supplied MATRIX diagram documents differential UART pairs; selecting and validating a suitable differential receive interface is a separate step.
