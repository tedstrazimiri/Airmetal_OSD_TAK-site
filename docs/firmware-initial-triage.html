Deeper firmware pass

The user explicitly redirected work to firmware reverse engineering before further hardware tests. The following extends the initial triage, without claiming a decoded firmware image.

Structure and decoding

An independent bounded probe, scripts/firmware_structure_probe.py, recorded results in evidence/firmware/structure-probe.json:

  • Bytes 0–7 are 1a 03 00 00 13 06 00 00, or little-endian integers 794 and 1555. Neither field's meaning is known. Calling this an eight-byte header remains a hypothesis.
  • The remaining 5,907,163 bytes have entropy 7.99996954 bits/byte and byte-frequency chi-square 249.35 with 255 degrees of freedom. This is compatible with near-uniform byte values, not proof of encryption.
  • No repeated 8- or 16-byte blocks within any tested alignment; no runs of four identical bytes. Tested byte-lag correlations from 1 to 65,536 show no strong periodic pattern.
  • Additional signatures for Zstandard, LZ4, Lzip, CAB, RAR, FIT, ELF and SQLite found no candidates.
  • Raw LZ4 rejected starts 0–256. Raw DEFLATE accepted only trivial candidates producing 0, 1 or 5 bytes while leaving essentially the whole file unconsumed; these do not recover a payload.
  • Tested 4,096 of 6,024 syntactically possible zlib header positions; all tested candidates rejected. This scan is explicitly incomplete.
  • No matches for the tested CRC32/Adler32 tail layouts or the narrow Cortex-M vector-table hypothesis. Other checksums, layouts, CPUs and address ranges remain possible.

The file length is not compatible with an eight-byte header followed only by block-aligned 16-byte ciphertext. Different header/trailer framing, stream modes and custom encoding remain possible. No encryption algorithm or key has been identified.
