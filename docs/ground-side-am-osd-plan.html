Ground-side AM_osd in ORQA GCS: implementation investigation

Prepared 2026-11-05. Scope: ground-side TAK situational awareness and the compact HUD references. This is an implementation plan based on saved bench evidence and current source, not a wiring release or a hardware acceptance result.

Recommendation: develop an external ground overlay unit near TAC, on the GU QS → TAC MATRIX return. Keep the control and telemetry link physically continuous; intercept only the video return, and obtain aircraft telemetry through a separate receive-only tap. A ground gateway receives TAK data and prepares display state; AM_osd composites that state into analog video before TAC sends it to the goggles. Prove single-ended video and text first, then the MATRIX adapter, then the SA graphics.

The user authorized treating the repository as the design baseline despite the physical PCB revision being unknown. Use its inline rev 0.3 family for planning. Confirm connector population and installed image during bench identification rather than blocking software preparation.

Proposed signal paths

Target location is the controller end of the GU QS–TAC cable. This keeps the new gateway and OSD accessible beside the operator. The following is a functional design, not an electrical schematic:

GU QS ── C2, telemetry, power: continuous MATRIX path ─────────── TAC
  │                                                              │
  └─ differential video return                                   └─ existing LEMO → goggles
       → matched CVBS receiver/conditioning
       → AM_osd VIDEO_IN → overlay → VIDEO_OUT
       → matched differential video driver → TAC video input

Telemetry pair ── high-impedance receive-only interface ──┐
TAK endpoint / selected CoT feed ─────────────────────────┼─ ground gateway
Initial local page selector ─────────────────────────────┘
Ground gateway ── dedicated 3.3 V UART / ground display protocol ── AM_osd

MATRIX documentary contacts are C2 1/2, telemetry 3/6, power 4/5 (+50 V/GND), video 7/8. Pin numbering/orientation must follow the source image. These are not Ethernet or standard PoE signals. Do not route 50 V through AM_osd's +5 V or VBAT connector pins.

The adapter must establish video differential amplitude/common mode, polarity, impedance, sync and existing equalization. Merely attaching a generic balun is not a demonstrated solution. TAC's cable-length setting commands its STM32 subsystem; whether it adjusts video equalization is still unknown. The insert must avoid fighting or duplicating that conditioning.

For the first prototype, power AM_osd/gateway from an independent regulated source suited to the board. Evaluate a protected MATRIX-powered supply only after load, transient and grounding measurements. Preserve pair geometry and existing termination; do not add another 100-ohm terminator to a live link by assumption. The telemetry tap must not transmit into either MATRIX lane. If a transceiver is used, hold its transmit driver disabled in hardware.

Placement decision gate: validate video extraction/reinjection at MATRIX before final PCB layout. If it cannot meet the video/equalization requirements, investigate a documented single-ended point after TAC conditioning, potentially on the goggles output. That would change the physical placement and needs a verified LEMO pinout; it is a fallback investigation, not a currently available connector solution.

Gateway and telemetry strategy

Start the gateway on this laptop, using recorded data. Package it on a small dedicated ground host only after its actual I/O, latency, power and enclosure needs are measured. No particular additional computer or adapter has been selected or reserved. Relevant inventory searches found no AM_osd, G431, differential receiver or measurement instrument records; this does not establish absence of unrecorded equipment.

The gateway has three responsibilities:

  1. Decode captured Ghost telemetry, preserving raw bytes, provenance and per-field freshness. Reuse the existing decoder as an offline oracle, not as proof of a validated live link.
  2. Receive an explicitly configured TAK feed, normalize marker identity, location, type, label, timestamps, expiry and deletion, and compute local displacements/MGRS. Keep credentials, XML/protobuf, history and network reconnection on the host.
  3. Supply bounded display state to AM_osd. The PCB owns the scanline-critical rendering; it does not become a TAK server or regional map database.

The official TAK protocol description distinguishes legacy CoT XML from negotiated protobuf framing. Choose and test one actual endpoint/export first. Do not assume every ATAK connection emits raw XML, nor infer ORQA's TAK integration transport from a manual capability claim. Saved CoT files are the first integration fixture; connecting a live endpoint is a later bench activity.

The current Betaflight GHST sender puts GPS ground course in 0x26 and a separately flagged magnetometer heading in 0x27. This explains why the reconstruction's UI label heading_degrees must not be taken as proof of aircraft nose heading. Current TAC dispatch analysis recognizes 0x26, not 0x27; a raw telemetry tap may expose more than TAC processes, but that is a hypothesis to test. Upstream protocol support does not establish support by this installed radio/FC.

Without usable ownship position, suppress relative marker ranges/plots. Without usable azimuth, suppress heading-relative arrows and the proposed heading-up/fan pages. A separately labelled north-up engineering diagnostic can help develop ingest, but does not accept the prototype's aircraft-heading behavior. The ground host's or operator phone's heading is not a substitute for aircraft heading.

If the passive capture lacks usable azimuth, first establish whether the installed radio forwards the standard magnetometer packet when the FC supplies it. If that route is unsupported, investigate a documented attitude/MSP telemetry route and a minimal aircraft telemetry change as a separate implementation dependency. TAC USB is a supplementary route only after a new capture proves the needed fields. Full heading-up SA is a go/no-go gate on this evidence; ground placement alone does not guarantee that every required aircraft field is available.

Use configurable, separately measured age limits for ownship position, azimuth, marker source and link health. Record sample time and arrival time independently. CoT stale is an expiry input, not a timestamp to rejuvenate on cache retransmission. After time discontinuity, gateway restart, origin change or sequence rollback, invalidate the dependent state until re-established.

Preserve the storyboard behavior

The design reference is TAK SA plus the compact HUD and feature request.

  • Normal HUD: add the nearest two fresh contacts, range/direction and own MGRS when their inputs are usable. Validate the remaining field contracts incrementally.
  • P06: centred ownship, heading-up God's-eye plot, initial 1 km range and four rings.
  • P07: forward fan, initial ±50 degrees and 3 km range. This is schematic TAK data, not a radar sensor or camera projection.
  • P08: remove expired/unavailable contacts and show TAK stale. Ownship/heading failure has a separate state; feed health does not establish navigation health.
  • P09: ownship/selected-marker MGRS, full independent prefixes, WGS84, explicit grid resolution and independent invalidation. Grid resolution is not positioning accuracy.
  • Nearest-two ordering considers all fresh bounded contacts, independent of the plotted sector/range. Zero range has no direction arrow; off-scale chevrons convey bearing only.

SA pages retain only average cell voltage from the legacy FC layout. A ground board can clear its own canvas, but cannot clear FC text already embedded upstream while restoring the hidden scenery. Recommended production direction: leave a small agreed set of essential aircraft-generated fields in fixed regions and let the ground unit own the additional HUD/SA fields. Reproducing the exact voltage-only SA reference requires a verified upstream OSD profile/suppression mechanism coordinated with page selection. Until that works, use a clearly labelled additive engineering preview; do not claim exact storyboard acceptance. Full opaque masking hides the camera beneath it and does not satisfy the undimmed God's-eye design.

The present compositor selects camera pixels or opaque black/white. Its brightness controls are not general scene alpha blending. Keep the SA prototype's grey/dimmed backgrounds as presentation references until either a measured approximation or a revised analog display treatment is accepted. Port rings, fan, markers and labels as bounded scanline/span primitives rather than assuming a full framebuffer will fit.

Current main's camera-2 AUX selection is a separate function. SA remains independent of camera angle and must not reuse that selector automatically. No new AUX assignment is made by this plan.

For Stage 1, existing firmware can receive host-generated MSP DisplayPort text. It also sends its own MSP attitude/RC/status requests; the bench host must handle/ignore them deliberately and suppress local features that would draw misleading crosshair/payload information. Do not fake attitude, arm status or release state to make the board appear connected. Do not use MSP_SET_OSD_CANVAS as page switching.

For Stage 5, introduce a new proposed bounded API: protocol version, session/sequence, monotonic age budget, source time/expiry, page/mode, coordinate-frame/origin identity, separate validity bits, ownship state, a capped marker list and explicit replacement/deletion semantics. Start with at most eight contacts as a design proposal, then size it from actual linker/runtime and UART measurements. Commit complete snapshots atomically; invalid/incomplete packets cannot partially update the page. Reserve bandwidth for framing, checksums, responses and error recovery. Parsing/projection happens outside the scanline interrupt.

Stage 3 must explicitly address power loss: repository rev 0.3 bypass is powered-reset bypass, not unpowered fail-through. A removable hard bypass is adequate for early bench experiments. A field unit needs a measured fail-through solution for the whole video adapter, not just the OSD switch. No latency number, cable-length limit, runtime margin or control-link neutrality is accepted by this document.

Immediate next step and completion state

Next hardware step: prove the repository-baseline AM_osd on an isolated single-ended PAL source/monitor with a constant host-generated AM GROUND overlay. Record VIDEO_IN/OUT, power/reset and bypass behavior. Keep it outside MATRIX until that passes. This is one bounded setup, not a request to connect a laptop or TTL adapter to MATRIX.

The next software implementation is Stage 0: a replayable gateway contract and DisplayPort text-output harness, using the existing SA fixtures before a live TAK or aircraft connection. This plan does not implement that harness.

This investigation completed the source/evidence review, architecture proposal and staged acceptance plan.
