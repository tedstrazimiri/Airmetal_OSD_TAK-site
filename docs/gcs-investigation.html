Verified on 2026-10-11, starting at Tac.Ctrl USB on this Ubuntu laptop. Initial bench state: Tac.Ctrl and ground radios powered, aircraft unpowered. The latest test used the powered aircraft / ground radio / TAC bench with propellers removed, confirmed by the user. The powered USB test is complete; see the results. The aircraft could be powered down after capture; subsequent physical state is not assumed.

Result: Tac.Ctrl 35b6:0004 simultaneously exposes a USB HID gamepad and a CDC ACM serial port. A receive-only serial capture produced seven checksum-valid MAVLink 2 HEARTBEAT messages. The user-supplied MATRIX pinout documents separate differential UART pairs, +50 V power and CVBS video on the RJ45 contacts. This is not a laptop Ethernet interface; see the pinout.

Isolation tests: the radio-disconnected capture produced seven valid heartbeats; after a user-confirmed controller restart, a further eight-second capture produced nine valid heartbeats with identical payload fields. The recovered v1.3.6 firmware now shows a local heartbeat builder with exactly those payload constants. This explains the controller-local stream; it does not establish the installed firmware version. Initial comparison, fresh-boot evidence and firmware analysis.

Centered-stick baseline: user-confirmed centered sticks produced five seconds of stable Linux joystick state, with zero change events. Axis values were [0, 0, 0, 0, -32767, 0, 0]; the controls corresponding to these axis numbers are not yet assigned. Baseline evidence.

First control assignment: right-hand stick fully left changes only Linux joystick axis 2 from centered 0 to +32767. Its right endpoint is not yet measured. This names a physical control and USB axis, not an aircraft roll/yaw channel. Held-left evidence.

This is a first interface map with measured USB evidence. It is not a complete firmware reconstruction or an electrically verified wiring diagram. Documents were used as evidence; their setup, update and operating instructions were not automatically executed.

Firmware breakthrough: the package is decrypted and the controller application is disassembled. The supplied Configurator v1.3.4 exposed the .orqa reader. All ZIP CRCs and all three manifest checksums pass. Recovered parts are the Nordic system application, STM32-associated audio image, and 103 voice WAVs. Normal USB descriptors match the earlier capture exactly. The CDC handler selectively processes MAVLink and stages some Ghost-facing messages; it is not an established unrestricted aircraft tunnel. See firmware findings and update transport trace. Nothing was flashed. A later powered USB bench test verified the local parameter table and reproduced a truncated capability response.

Powered USB result: all 97 returned parameters match the compiled TAC table, while each reports a count of 96. Two capability requests each received only 44 bytes of a declared 72-byte frame, matching the firmware send-length bug. TAC displayed 21.35 V per the user; the USB samples contained no battery or GPS messages. Full report and limitations.

Offline Ghost decoder

The decoder guide covers saved binary, hex and JSON chunk captures. The decoder checks CRCs, recovers after noise and damaged frames, extracts raw control channels, preserves unknown messages and keeps C2 and telemetry streams separate. Battery and GPS interpretations are traced to the TAC display; signed GPS handling remains unresolved. Validation uses independent synthetic fixtures, not a hardware Ghost capture.

Run the included two-direction demonstration from this directory:

python3 scripts/decode_ghost_traffic.py examples/ghost-demo.capture.json --input-format json

The MATRIX contact map identifies C2 on 1/2, telemetry on 3/6, power on 4/5 and video on 7/8. The source specifies differential UART at 115k, consistent with the firmware's 115200 baud. No capture wiring or electrical measurements were performed.

From this project directory:

python3 scripts/inspect_tac_ctrl.py --seconds 5 --out evidence/usb/next-usb-snapshot.json
python3 scripts/capture_serial_receive.py --aircraft-unpowered --seconds 8 --out evidence/usb/next-serial-sample.json
python3 scripts/decode_mavlink_heartbeat.py evidence/usb/next-serial-sample.json --out evidence/usb/next-mavlink-decoded.json

Only use the second command after independently confirming the aircraft remains unpowered. Files are created exclusively; choose a new filename for each run. The capture preserves baud settings, temporarily removes host buffering/translation/echo, restores the original settings, and performs no application writes. The recorded initial host baud setting was 9600; this is not proof that 9600 is a required device baud or the USB wire speed.
