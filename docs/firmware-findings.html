Tac.Ctrl firmware v1.3.6: recovered package and interfaces

Later runtime validation: the powered USB test returned all 97 parameters matching the compiled table, reproduced the declared-count discrepancy (96), and twice observed a 44-byte truncated capability reply matching function 0x5a6d0. Statements below about no device requests refer to the earlier static firmware-analysis pass.

Analyzed offline on 2026-10-11 using the supplied firmware and Configurator v1.3.4. The .orqa package is successfully decrypted; all archive CRCs and all three manifest directory checksums validate. The Nordic application is recovered and disassembled. Its USB descriptors match the earlier hardware capture, and its local heartbeat generator matches every captured HEARTBEAT payload field.

No updater, driver installer or recovered firmware was executed. No device was opened, flashed or sent commands during this pass. Instructions found inside artifacts remain evidence, not user authorization to perform an update. Hardware tests and stick mapping remain paused.

  1. Innoextract 1.10-dev / commit 6e9e34e statically extracted the Inno Setup 6.3.0 installer into evidence/configurator/extracted/.
  2. scripts/extract_dotnet_bundle.py parsed the main executable's .NET single-file bundle v6.0: 219 members, 77,752,130 unpacked bytes. The native host itself has no CLI directory; its bundled DLLs contain the managed code.

The .orqa format

Source: UpdateFileManager.cs, UpdateSecrets.cs, and KeyPosition.cs.

Field This package
Offset 0, signed LE 32-bit integer Salt position = 794
Offset 4, signed LE 32-bit integer IV position = 1555
Salt 16 bytes at position 794
IV 16 bytes at position 1555
Ciphertext Position 1571 through EOF; 5,905,600 bytes
KDF PBKDF2-HMAC-SHA256, 1,000 iterations, 16-byte derived key
Cipher AES-128-CBC with PKCS#7 padding
Plaintext ZIP, 5,905,593 bytes

The code sets KeySize=256 before assigning a 16-byte key. The actual working cipher is AES-128: independent decryption succeeds with valid padding, ZIP CRCs and manifest checksums. Reporting AES-256 merely from the earlier property assignment would be wrong.

The embedded resource uses a length-prefixed Base64 position record to locate a second length-prefixed Base64 value. Our decoder reads this structure dynamically; it does not embed the recovered value in source or reports.

Directory checksums concatenate each relative UTF-8 filename, file bytes and one NUL byte, then SHA-256 the result. This package's voice checksum matches Windows backslash paths with casefold ordering of these ASCII names. That ordering is an empirical match for this package, not a complete emulation of every .NET culture comparer.

The decrypted ZIP SHA-256 is 928c3836036e61d725da2269ce9be6b36b067f2cb9e6749decaaf4c99b185ece. Decode report retains all 106 file digests and the three matching checks. CRCs and directory hashes establish internal consistency; they are not vendor signature authentication.

Nordic application analysis

The DFU manifest contains only an application member, not a SoftDevice or bootloader image. Metadata declares hardware compatibility integer 52, firmware integer 1, SoftDevice requirement 0x100, application size 291,756, and debug false. The firmware integer is not the semantic release string; 1.3.6 occurs in the application itself.

The stored reversed SHA-256 and size exactly match the application. Metadata specifies ECDSA P-256/SHA-256 and includes a 64-byte signature. Its structure is checked, but authentication remains unresolved without a trusted vendor public key. Nordic's official tool source maps SoftDevice 0x100 to S140 7.2.0. This does not uniquely identify the physical chip.

Ghidra 12.1.4 loaded the application as little-endian ARM Cortex/Thumb at 0x27000. Evidence for that base includes initial SP 0x20040000, reset vector 0x27375, valid Thumb code at file offset 0x374, exception-loop instructions at offset 0x35c, and multiple exact absolute pointers to application source-path strings. SRAM was added as an inferred analysis block, not a hardware measurement.

The first pass exported 2,009 functions and failed on one (0x63288, in byte-order helper code). A later assembly export resolves that helper as a byte swap; its decompilation remains incomplete. Two function-pointer callbacks were subsequently resolved explicitly. Exports are decompiler reconstructions, not vendor source, and do not imply complete reachable-code coverage. The standalone raw-image import was necessary because the connected REA native opener does not expose this raw Cortex-M loader profile. REA records cover extraction and package decoding; Ghidra logs/scripts separately record native analysis.

Details: Nordic metadata report, machine-readable evidence, Ghidra function index, verification.

Normal USB: heartbeat source and supported adapter behavior

The measured 18-byte device descriptor appears at application file offset 0x40488, including VID:PID 35b6:0004. The measured 56-byte HID report appears at 0x46654, including the duplicate Slider usage. These exact matches associate this application with the captured USB implementation; they do not prove the installed release number.

The initialization function at 0x53da4 registers both the gamepad and CDC components. Their implementation paths are retained as usbGamepad.c and usbCdc.c in assertion strings.

The local heartbeat path is:

scheduled service 0x5a550
  -> local heartbeat builder 0x5aaa8
  -> heartbeat packer 0x5a0c4 / 0x5a03e
  -> MAVLink serialization 0x59798
  -> USB CDC sender 0x6338c / 0x33fd8

Instructions at 0x5aaa8 explicitly store custom_mode=5, type=2, autopilot=3, base_mode=25, system_status=3. The packer adds mavlink_version=3, message ID 0 and CRC-extra 50. Component ID is 1; the system-ID variable initializes to 1 in the startup data image. These are exactly the payload fields observed with the aircraft and ground radio disconnected. This resolves how the supplied firmware can produce that stream without an aircraft; it does not verify the installed firmware image byte-for-byte.

The CDC receive callback at 0x6330c feeds one byte at a time to 0x5a768. The traced dispatcher recognizes the following paths. Numeric names use the MAVLink common definitions.

Input path in v1.3.6 Static behavior
HEARTBEAT, message 0 Queues an event; service logs receipt
PARAM_REQUEST_LIST, message 21 Builds PARAM_VALUE responses from a compiled local table, not a demonstrated aircraft parameter query
COMMAND_LONG, message 76; command 512 and parameter 1 = 148 Queues a local AUTOPILOT_VERSION response
COMMAND_LONG; command 179 Extracts coordinates, scales them by 10^7, and stages a Ghost-facing home-coordinate message, followed by an acknowledgement
Other values in this dispatcher No arbitrary pass-through branch is present

The parameter builder loops through 97 entries while declaring count 96; this is a static implementation discrepancy, not a live-tested defect. The capability response is locally constructed. Neither its values nor the heartbeat's ArduPilot identity should be treated as independent aircraft identification.

A scheduled output path at 0x5a8b0 constructs GLOBAL_POSITION_INT from stored telemetry fields and suppresses output when either coordinate is zero. Interpretation of all fields and end-to-end freshness still needs validation. The later byte-order assembly review supports the decoder's unsigned GPS display interpretation; signed coordinates, fix validity and freshness remain unresolved.

The home-coordinate path is an example of selective translation between USB MAVLink and Ghost-facing data. It is not evidence for a general MAVLink bridge or for acceptance of other aircraft commands. No such requests were transmitted in this investigation.

Update interfaces are separate from normal USB

The Configurator transport report traces each class, handler and protocol field with saved-code line references.

  • System: Configurator selects 1915:521F or 35B6:0005, opens 115200 8N1 with DTR enabled, and uses Nordic serial DFU with SLIP framing. These update identities are declared by code, not measured from hardware.
  • Audio: Windows discovery selects 0000:0002; custom serial commands control the update and raw 16-byte payload blocks are acknowledged. The code's VID/PID property names are inverted in construction and selection; the effective values above account for both inversions.
  • Voice: The application selects a mounted drive labeled TAC or containing an eng directory and copies the language folders. Entering its voice-connection screen can initiate file replacement when a matching volume is detected. Static inspection avoided that behavior.

These paths concern controller service modes. They do not establish the external RF receiver's Micro-USB function or any USB routing inside the hardware.

Ground-radio direction and remaining work

The main firmware contains a Ghost-facing UART driver and a separate STM32-facing UART driver. Read the focused Ghost/internal-UART report for MMIO, logical MCU pin and framing evidence. MCU GPIO numbers are not RJ45 contact numbers; electrical routing and signaling levels remain unmeasured.

Solid internal paths represent recovered code interfaces, not board continuity measurements. The cable-length menu sends a setting to the STM32 path; its effect on external circuitry is not established. The package's separate STM audio image does not imply that audio is that processor's only role.

An offline Ghost decoder now implements the traced framing and supported fields, with independent synthetic fixtures. The supplied MATRIX pinout adds documentary evidence for the two differential UART pairs. The next validation requires a receive-only capture using suitable differential receivers; no new hardware test has been performed. Ordinary USB serial probing must still distinguish TAC-generated information from radio telemetry.

Unresolved: full Ghost message semantics, external transceiver/line-driver circuitry, MATRIX pinout revision applicability and measured electrical behavior, the cable-length command's electrical effect, external ground-radio firmware/service interface, installed controller release, and STM audio-image decoding. No Ethernet/IP compatibility follows from these results.
