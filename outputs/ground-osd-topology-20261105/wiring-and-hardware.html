Ground AM_osd topology — Raspberry Pi 4B prototype

2026-11-05. Open the interactive diagram, topology PNG, or pinout PNG. Vector originals: topology and pinouts. The hardware CSV gives purposes, endpoints and selection status.

Decision: use the Pi 4B as the prototype gateway. Its UART, USB and network interfaces fit TAK ingest, Ghost decoding, coordinate conversion and display updates. AM_osd remains the analog video compositor. This is an engineering suitability judgment, not a measured latency or load result. A headless service with bounded contacts avoids processing video frames on the Pi. The Pi's TV jack is an output, so it does not replace the differential video receiver or accept the MATRIX feed.

The supplied MATRIX drawing is the contact authority. AM_osd inline rev 0.3 family is the board planning baseline, as authorized by the user. Actual harness contact orientation and installed image must match the repository before bench wiring. This package is a proposed topology, not an electrically accepted schematic or completed prototype.

1. MATRIX at both insert connectors

Use two bare 8P8C/RJ45 breakouts with adequate voltage rating/clearance and a short CAT6 patch lead. Avoid Ethernet magnetics or hidden PoE/balun circuitry. Keep the original twisted-pair geometry and short tap stubs. Number contacts using the supplied drawing; do not assign them from an assumed cable colour or a mirrored plug view.

Contact Function Proposed connection
1 C2_N Radio-side 1 straight to TAC-side 1; control direction TAC → radio
2 C2_P Radio-side 2 straight to TAC-side 2
3 TEL_N Radio-side 3 straight to TAC-side 3; high-impedance receive-only branch to U1 B7

5 GND Straight-through; common G0 reference for this non-isolated prototype

The document describes 115k full-duplex differential UART, with 100-ohm termination at the receiving end. It does not establish RS-422/RS-485 compliance or bus common mode. Preserve existing telemetry termination; do not fit an additional 100/120-ohm termination or bias network to the tap. No MATRIX wire reaches the Pi's Ethernet jack.

2. Pi ↔ AM_osd wiring

Pi / supply endpoint AM_osd endpoint Function
Physical 8, GPIO14 TXD J3 pin 4, board label TX6 / net FC_TX / MCU PA10 RX Gateway → OSD
Physical 10, GPIO15 RXD J3 pin 3, board label RX6 / net FC_RX / MCU PA9 TX OSD → gateway
Physical 6, GND J3 pin 2, GND Common G0, also referenced to MATRIX 5
Independent regulated +5 V J3 pin 1 AM_osd board power

The RX6/TX6 names are from the FC's perspective: J3.4 is AM_osd receive; J3.3 is AM_osd transmit. Both Pi and AM_osd UART logic are 3.3 V. Run 115200 8N1, no hardware flow control. Keep the TTL cable short. The USB telemetry input and the AM_osd UART are distinct serial devices.

Enable the Pi UART hardware, disable the serial login/boot console and assign a stable UART to GPIO14/15. On Pi 4, use the documented PL011/Bluetooth mapping if required for a stable clock. Check the running OS configuration rather than assuming a /dev/ttyAMA0 device identity. Use one serial writer for AM_osd; do not allow console or management traffic onto it.

Existing MSP DisplayPort can carry a text proof. The gateway must deliberately handle the board's outgoing MSP requests and suppress inappropriate local crosshair/payload drawing. SA rings, fan, markers, page takeover and a bounded state API remain firmware work. Do not use MSP_SET_OSD_CANVAS as a page selector.

3. Receive-only telemetry interface

U1 is a candidate TI THVD1450D (8-pin SOIC) circuit, powered at 3.3 V. It is not yet proven compatible with MATRIX. Confirm bus common mode, idle polarity, input loading and physical protection first. A breakout must allow removal/disabling of termination and bias resistors.

U2 is a documented USB-to-3.3 V UART adapter, for example an FTDI-class adapter. Its TXD, RTS, CTS and power lead stay unused/insulated. A 3.3 V logic adapter may still expose 5 V on its power lead. Select by the actual adapter data sheet; no universal USB adapter header numbering is assumed here. U1's disabled driver is the protection against software accidentally sending data into MATRIX.

Capture at nominal 115200 with separate lane provenance. A second identical U1/U2 chain may later receive C2: MATRIX 2 → A6, MATRIX 1 → B7. It remains optional; select SA pages locally on the Pi first. Physical RC mapping and AUX conflict checks are separate work.

4. Analog video endpoints and bypass

Stage Functional wiring Suggested building block
V1 differential receiver Radio MATRIX 7/8 via K1A → IN−/IN+; single-ended output → AM_osd J1.3; return → J1.2 / G0 AD8130-based evaluation circuit
AM_osd J1.3 VIDEO_IN → analog compositor → J2.3 VIDEO_OUT Existing inline PCB
V2 differential driver AM_osd J2.3 → CVBS input; OUT−/OUT+ via K1B → TAC MATRIX 7/8; return → J2.2 / G0 AD8132-based evaluation circuit

J1/J2 pins 1,4,5,6 are unused in this ground harness. Their copper pass-through does not power the OSD. The video ports above are functional endpoints, not AD8130/AD8132 package pin numbers. Do not wire those ICs without a proper circuit: feedback, gain, output common mode, source/load impedance, decoupling, supply rails and any equalization must be designed from measured MATRIX video. Pi micro-HDMI/TV-out and generic CCTV baluns are not replacements for this qualification.

K1 needs four changeover signal poles, for example two DPDT signal relays operated together. A single 4PDT manual switch can establish the topology on the bench if its signal integrity is acceptable. Contact/coil pin numbers depend on the selected device. Logical contacts are:

Logical pole COM NC, default bypass NO, overlay mode
K1A-N Radio MATRIX 7 Join to K1B-N NC V1 IN−
K1A-P Radio MATRIX 8 Join to K1B-P NC V1 IN+
K1B-N TAC MATRIX 7 Join to K1A-N NC V2 OUT−
K1B-P TAC MATRIX 8 Join to K1A-P NC V2 OUT+

This transfers both ends of the active branch. In bypass, V1's receiving-end termination and V2's driver are disconnected. Leaving V1 terminated across the line while bypassing its output would create a second load on the original TAC video link. In overlay mode, provide the correct new receiver termination and restore a compatible signal to TAC; do not transplant the UART's 100-ohm note into a video design without measurement.

For initial bench tests use deliberate local bypass selection. A later relay implementation needs rated drive circuitry, flyback handling, a de-energised bypass default, and health supervision independent of Pi software. Verify transition behavior and power-loss recovery for the whole V1/OSD/V2 assembly. AM_osd's own powered-reset bypass does not cover loss of its supply.

5. Suggested hardware summary

Required additions around Pi + AM_osd are two bare MATRIX breakouts/patch wiring, one conditional receive-only differential UART circuit, one USB-to-3.3 V UART adapter, matched differential CVBS receiver and driver circuits, a four-pole bypass, independent bench supplies, and measurement/source/display equipment. The hardware CSV gives each endpoint and purpose. Model suggestions are candidate circuits, not a purchase-ready BOM.

Power Pi via its own good-quality USB-C 5 V / 3 A supply. Power AM_osd at J3.1 from a separate regulated 5 V output. Use suitable analog bench rails for the selected V1/V2 circuit; these are not assumed to be 3.3 V or GPIO-powered. All indicated returns join G0 in this non-isolated prototype. Evaluate grounding and backfeed before connection. MATRIX 4 stays pass-through only.

Use a differential oscilloscope measurement suitable for the actual common-mode voltage, plus a known PAL source and monitor. Start with AM_osd alone. Next compare unloaded MATRIX with the receive tap/insert, then verify sync, levels, picture, latency and control/telemetry continuity. Keep aircraft outputs inactive during wiring tests.

Relevant inventory was checked. HW-0007 records two owned Pis with unresolved batch models and a separately observed Pi 4B bench context; availability for this project is unconfirmed. This design proposal does not allocate either Pi or transfer equipment from the Ascent project. Relevant receiver/test-equipment searches found no matching inventory entries, which does not establish absence of unrecorded equipment.

6. What remains open

MATRIX electrical characterization; actual aircraft azimuth/fix/source-time availability; clean-SA versus baked airborne OSD ownership; live TAK endpoint; bounded SA firmware/render budget; whole-unit bypass behavior; analog goggles/DVR acceptance. No Pi video throughput claim or flight readiness follows from this diagram.

At 115200 8N1 the theoretical UART ceiling is 11,520 bytes/s before protocol overhead. A proposed 320-byte bounded display snapshot at 10 Hz would use 3,200 bytes/s before framing, requests and replies. This illustrates why a small state feed is plausible; it is not a finalized packet format or measured render/update rate.
