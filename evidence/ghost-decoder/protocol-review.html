Independent Ghost payload review for the offline decoder

Scope: static TAC 1.3.6 image (4c79b25623f07bfc62e8f223e8fbda30b0aba643277d9e13f1fadb6bd15931dd, Cortex-M base 0x27000). No decoder implementation imported, no hardware used, no Ghidra project writes. Sources below are saved artifacts under evidence/firmware/ghidra-export/, except the focused byte-order assembly under evidence/ghost-decoder/byte-order-helpers/.

fixtures-review.json contains literal synthetic frame hex and independently calculated expected values. They are not radio captures. CRC was calculated by GF(2) polynomial long division of the complete type+payload bit string, appending eight zero bits and dividing by polynomial 0x1D5; this is independent of a byte-at-a-time decoder CRC routine. The standard 123456789 check yields BC.

Framing boundary

0004c4a0.c:28–33,464–466 builds the 14-byte outgoing control frames:

81 0C <type> <10 payload bytes> <CRC>

Length counts type+payload+CRC, so total bytes = length+2. CRC covers type and payload only. 0004c428.c implements polynomial D5, MSB first, initial 0, no final XOR. The receive callback at 0x4be5c explicitly processes 14- and 27-byte frames and the dispatcher 0004cbf8.c requires address 80. The receive fragment accumulator also recognizes 90, but the shown dispatcher does not consume it; preserve 90 frames as opaque candidates.

For the offline decoder, do not interpret an 80 type 10 as a proven RC command or an 81 type 23 as telemetry: meaning depends on address/direction. Unrecognized types should retain raw payload with valid/invalid CRC status. The review establishes payload interpretation for the exact lengths below; malformed length must not be used to read missing fields.

Control types 10, 11, 12: exact bit order

Let p[0..9] denote payload bytes (frame bytes 3–12). The four first channels are:

ch1 = p[0] | ((p[1] & 0x0f) << 8)
ch2 = (p[1] >> 4) | (p[2] << 4)
ch3 = p[3] | ((p[4] & 0x0f) << 8)
ch4 = (p[4] >> 4) | (p[5] << 4)

Equivalent: four 12-bit values packed consecutively least-significant-bit first into the first six bytes. Source 0004c4a0.c:58–61,86–87,112–114,139–142.

Type p[6],p[7],p[8],p[9]
10 Channels 5, 6, 7, 8 as unsigned bytes
11 Channels 9, 10, 11, 12 as unsigned bytes
12 Channels 13, 14, 15, 16 as unsigned bytes

Sources: 0004c4a0.c:143–248, 250–356, 358–462. Return the exact transmitted numeric values. Do not multiply the byte channels by 16 or convert all channels to one assumed pulse-width range.

Scaling occurs before packing in resolver 0x521e4: source types 1–4 return stick-associated values with optional inversion around endpoints 0x159/0xE26 (345/3622); switch helper functions 0x52158, 0x5218a, 0x521bc emit values including 24,124,224; scroll source types 15/16 map input 0..2047 to 24..224 using integer affine mapping (000521e4.c:138–142, 000520b8.c). These are source mappings chosen by per-channel configuration, not fixed meanings of every channel number. A channel decoder should therefore expose raw transmitted values and bit widths, not recover physical controls from the number alone.

Hand-selected nibble fixture: 81 0c 10 23 61 45 89 c7 ab 18 7c e0 ff 15 decodes channels 1–4 as 0x123,0x456,0x789,0xABC and channels 5–8 as 24,124,224,255.

Received payload fields: intermediate state versus UI interpretation

This firmware has an important two-stage byte-order pattern. Handlers explicitly construct big-endian numeric intermediate values in RAM state 0x200056A8, but some UI consumers then reverse their bytes before displaying them. A field called simply voltage_raw can therefore be ambiguous. Preserve payload bytes and distinguish handler-state values from UI-end interpretation.

Assembly byte-order-helpers/00063288.asm shows input bytes copied to output positions 3,2,1,0 and returns the word: bswap32. 000632c2.asm swaps two bytes and returns with LDRH, hence a zero-extended bswap16. The truncated C decompilation of 0x632c2 is not an adequate source for its prototype.

The short telemetry fixtures use 10-byte payloads. The type24 fixture uses 23 bytes / total frame 27. Do not invent names for fields whose consumer semantics have not been traced.

Type 23: UI-supported battery fields

000620e8.c:15–33 applies bswap16 to each of state+28,+2A,+2C. Thus UI input is effectively LE u16 on the wire:

  • p0..1: LE u16 /100.0, displayed as Drone Volts, unit V.
  • p2..3: LE u16 /100.0, displayed as Drone Amps, unit A.
  • p4..5: LE u16 directly, displayed as Drone mAh, unit mAh.

Literal at 0x62418 is high double word 0x40590000, low word supplied as zero: 100.0. Division helper 0x638ac is the software double division routine (denominator reciprocation and quotient refinement in its saved export); 0x63c48 converts a signed 32-bit integer to double, but all inputs here are zero-extended 16-bit values, so no signed ambiguity affects these fields. Format %.2f is at 0x6d4e8.

String evidence: literals 0x62420→0x6d4f0='Drone Volts', 0x62424→0x6d4fc='V', 0x62428→0x6d500='Drone Amps', 0x6242c→0x6d50c='A', 0x62430→0x6d510='Drone mAh', 0x62434→0x6d51c='mAh'.

For payload 01 02 03 04 05 06 07 08 09 0A, raw handler BE values are 258,772,1286; UI values are 5.13 V, 10.27 A, 1541 mAh. The endian-trap fixture is deliberate.

Type 25: UI-supported GPS fields with a signedness limitation

000620e8.c:38–58 swaps state+2F,+33 using bswap32 and state+37 using bswap16. Effective wire fields:

  • p0..3 LE u32 /10,000,000.0, displayed as GPS Lat, unit deg.
  • p4..7 LE u32 /10,000,000.0, displayed as GPS Long, unit deg.
  • p8..9 LE u16 directly, displayed as Altitude, unit m.

The paired literals at 0x623f8=0 and 0x623fc=0x416312d0 encode double 10,000,000.0; format %.7f is at 0x6d530. Labels resolve through 0x62444→0x6d538, 0x6244c→0x6d544, 0x62454→0x6d558, with degree/metre strings at 0x6d540/0x6d564.

Do not silently assert signed geographic coordinates. UI converter 0x63c70 constructs double without sign-bit handling; in contrast, signed converter 0x63c48 explicitly masks bit31 and negates negative input. This makes the observed UI path an unsigned interpretation. A payload carrying bit31 can produce a number outside geographic range. The decoder can expose latitude_e7_raw_u32, longitude_e7_raw_u32, ui_latitude_unsigned_degrees, ui_longitude_unsigned_degrees and annotate the limitation. Interpreting those same bit patterns as signed two's-complement coordinates is plausible but not proven by this UI path.

received_type25_unsigned_ui_boundary intentionally verifies this boundary: the first LE word is 0x80000000, the second 0xFFFFFFFF. UI-equivalent values are 214.7483648 and 429.4967295, not claimed valid coordinates. Altitude zero-extends its 16-bit word, so signed negative altitude is also unproven here.

Other received types

The report provides handler raw fields for 26/32/33 and opaque payload for24. Type26 UI does name some fields (heading, satellite count, distance), but a complete consistent unit/signedness map is outside this bounded decoder review. Keep raw outputs instead of extrapolating standard GHST documentation to every field.

Fixture use

The JSON contains 12 literal frames: three control variants; 23/24/25/26/32/33; a high-bit GPS case; an unknown type; and a deliberately corrupted CRC. Expectations are precomputed and do not depend on production parser functions. They include all raw expected field values and applicable UI conversions. The malformed CRC fixture has the same payload as the first control fixture but last byte14 instead of15; it must not be accepted as valid decoded control data.

These fixtures establish decoding arithmetic and boundaries only. They do not validate the physical radio link, timing, serial framing at an electrical level, current installed firmware, or the interpretation of every packet type.
