Tac Configurator v1.3.4: static USB/update transport trace

Analyzed 2026-10-11. This report describes decompiled shipped code, not a hardware test. Neither the updater nor its driver was executed; no serial device was opened and no USB/flash commands were sent. The Configurator's three update paths concern the controller, not a demonstrated interface to the external ground radios.

Main finding

The application separates system firmware, audio firmware, and voice files into three update paths. Its system firmware path uses Nordic serial DFU, its audio firmware path uses a small custom ASCII/binary serial protocol associated by the application with STM32, and its voice-file path writes files on a mounted volume. This provides substantive evidence for separate controller system/audio firmware domains; it does not identify their exact silicon, physical USB switching, board wiring, or MATRIX/RJ45 pinout.

The code's UI names map Nordic to SYSTEM FIRMWARE, Stm32 to AUDIO FIRMWARE, and Voice to VOICE PACK: App/Orqa.TAC.Configurator.Assets.Lang.Resources.resx:55,61,64 below the decompilation root.

Decompilation root: [local workstation]/Documents/ChatGPT/REA - Orqa GCS/evidence/configurator/decompiled/. All file references below are relative to this root; line numbers refer to the saved decompilation, not vendor source.

Windows enumerates Win32_PnPEntity entries whose captions include (COM, extracts a COM\d+ name, and parses VID_ and PID_ values. A naming inversion is important: it constructs SerialPortInfo(port, parsedPID, parsedVID, caption) at Windows manager line 105; the constructor assigns its second parameter to property VID and third to PID (Core/Orqa.TAC.Configurator.Core.Data/SerialPortInfo.cs:15–20). The selection tests then reverse those properties, so the effective USB IDs above are correct. Quoting the property names alone would falsely reverse the hardware VID/PID.

No interface number is matched in the Configurator COM-port discovery. SingleOrDefault is used, so more than one matching COM entry can throw rather than select one. System-update discovery additionally requires the caption to contain USB (case-sensitive).

The Linux system discovery searches /dev/ttyACM* and invokes udevadm info -q property -n <device>; it compares strings to configured tuples without case normalization (TACLinuxConnectionManager.cs:28–48,76–90). Configured IDs include uppercase 521F and 35B6; raw case handling matters. Its STM selector is inconsistent with the Windows selector and uses the Nordic ID. These are observations of a Windows-distributed application's Linux code, not a claim that a supported Linux release behaves this way.

The previously measured normal-mode controller ID 35b6:0004 is not one of these updater selectors. The 35b6:0005 value is therefore a code-declared update identity, not yet a live descriptor observation. Bundled Nordic driver declarations, recovered separately in driver-payloads/*.inf, match generic Nordic DFU/CDC devices; they alone were not sufficient to establish this application-level association.

Overall update state flow

App/Orqa.TAC.Configurator.ViewModels.TAC/DescriptionViewModel.cs:71–115 conditionally processes manifest parts in the fixed order Nordic → STM32 → Voice, regardless of manifest display order, with a connection screen and completion wait for each included type. A manifest does not have to contain all three types.

For Nordic/STM, opening the corresponding screen starts device enumeration approximately every 100 ms; the Next button calls the appropriate handler only after a device is found. See App/Orqa.TAC.Configurator.ViewModels.TAC.Connection/ConnectNordicViewModel.cs:84–134 and ConnectStmViewModel.cs:84–134. App/Orqa.TAC.Configurator.Services/UpdateService.cs:48–61 awaits the handler and tracks success/failure.

The packaged UI text describes three modes. This is evidence, not a request to put the hardware into these modes:

  • System: middle navigation button held during power-on; screen Controller Update (Resources.resx:32,52).
  • Audio firmware: up and down navigation buttons held during power-on; screen Updating sound system... (Resources.resx:40,42).
  • Voice files: CONTROLLER SETTINGS → Change voice pack; screen Ready! Transfer files. (Resources.resx:43,62).

Nordic/system firmware serial transport

Call chain: NordicUpdateHandler.RunAsync chooses the manifest's Nordic part and sets its extracted path (App/Orqa.TAC.Configurator.Services.Update/NordicUpdateHandler.cs:34–46); TACUpdateManager.UpdateAsync passes that path and selected COM port to NRFUtilLibWrapper.RunDFU (Core/Orqa.TAC.Configurator.Core/TACUpdateManager.cs:21–24). The wrapper loads a Nordic ZIP, constructs DfuTransportSerial(portName, 16) and starts DfuOperation (Core/Orqa.TAC.Configurator.Core/NRFUtilLibWrapper.cs:26–39).

The bundled Nordic.nRF.DFU.dll was separately decompiled to Nordic/ for this trace, with the same local ILSpy 9.1 toolchain. No library methods were invoked.

Port and framing

Nordic/Nordic.nRF.DFU/DfuTransportSerial.cs:82–119 creates a port with:

  • 115200 baud, 8 data bits, no parity, one stop bit;
  • DTR enabled, handshake none;
  • receive buffer 4096, transmit buffer 2048;
  • read/write timeout 5000 ms;
  • up to 50 port-discovery attempts separated by 200 ms.

The USB line-coding value does not establish an internal UART's physical bit rate.

Commands and data are SLIP-encoded. The encoder wraps with C0, escapes data C0 as DB DC and DB as DB DD; the serial writer deliberately removes the initial C0, leaving an escaped payload plus trailing C0. Firmware data is prefixed with command byte 08 before encoding. Sources: Nordic/Nordic.nRF.DFU.Util/SLIPEncoder.cs:7–39; DfuTransportSerial.cs:47–62.

Responses must decode as 60 <request_opcode> <status> <payload>. Status 01 is treated as success. Expected response opcode and payload length are checked, and response waits time out after five seconds. Sources: Nordic/Nordic.nRF.DFU/DfuTransportPrn.cs:33–64,80–139; ErrorCode.cs:5–6.

The ordinary update call chain uses setup, select/create/write/CRC/execute operations; the presence of version-query methods does not establish that the application calls them or that the controller supports them. No ping opcode was found in these classes.

DfuTransportSerial.Ready first sets PRN=16, then obtains MTU. The maximum unencoded data length is calculated as integer wireMTU / 2 - 2, rounded down to a multiple of four. It is negotiated, not hardcoded as one universal packet size.

Nordic/Nordic.nRF.DFU/DfuOperation.cs:36–54 sends each update's init packet before the firmware image. DfuAbstractTransport.cs:29–39 uses object type 1 for init and type 2 for firmware; :42–149 implements object selection, resume using reported offset/CRC, object-sized chunking, create/write/check/execute, and bounded retry after CRC failure. CRC polynomial is reflected 0xEDB88320 with initial/final inversion (Nordic/Nordic.nRF.DFU.Util/CRC32.cs:8–29).

The ZIP reader selects manifest.json, resolves .dat init and .bin image entries, and supports application, bootloader, SoftDevice, or combined SoftDevice/bootloader members (Nordic/Nordic.nRF.DFU/DfuUpdates.cs:35–95). Supporting those members in generic code is not evidence all are present in this firmware package.

STM32/audio firmware protocol

STMUpdateHandler chooses the manifest Stm32 part and calls VoiceFirmwareUpdater.Update with the selected STM port (App/Orqa.TAC.Configurator.Services.Update/STMUpdateHandler.cs:34–45). UI labels it AUDIO FIRMWARE; it is not the Nordic main-system updater.

Core/Orqa.TAC.Configurator.Core/VoiceFirmwareUpdater.cs:27–62 opens new SerialPort(portName, 115200). Other settings are not explicitly overridden in this class. The observed code sequence is:

  1. ASCII #$ERASE_MEM, then response check and 100 ms delay.
  2. ASCII #$FLASH_START, then response check and 100 ms delay.
  3. Repeated raw 16-byte firmware blocks, waiting for a response containing the case-sensitive text OK after each block.
  4. 100 ms delay, ASCII #$FLASH_FINISH, response check, another 100 ms delay.
  5. ASCII #$BOOT_UP, response check; percentage becomes 100.

Commands are written without CR/LF or length prefixes (:65–78). A command response is considered successful if the first currently available bytes do not contain ERROR case-insensitively; there is no specific affirmative token requirement for these command responses. The code polls every 10 ms until some bytes arrive; no bounded timeout is implemented in these polling loops. Data block responses require OK (:81–102).

No block sequence number, address field, host-side checksum, or host-side CRC is added by this class. That does not exclude validation within the device bootloader. The loop sends floor(fileLength / 16) blocks, so a non-multiple-of-16 tail would be omitted by this implementation. No port close/dispose appears in the class. These are implementation limitations, not tested device faults.

Voice files / mounted volume path

This path operates through filesystem APIs rather than COM-port protocol. Windows accepts ready removable drives; Linux accepts ready mount roots under /media/ or /mnt/. A drive is considered TAC if its volume label is exactly TAC or it contains a root eng directory (VoicePackUpdateManager.cs:243–285). It does not inspect USB VID/PID or serial identity.

The connection screen starts monitoring immediately; the manager enables a watcher and polls every five seconds. On a matching drive it reports detection and immediately invokes ProcessTacDevice, before the Next-button handler (App/Orqa.TAC.Configurator.ViewModels.TAC.Connection/ConnectAudioViewModel.cs:77–108; Updates/Orqa.TAC.Configurator.Encryption/VoicePackUpdateManager.cs:77–90,219–225). This is a material reason not to launch this updater merely to inspect devices.

It looks for tacupdate in the system temporary directory or a child of it, then enumerates its voice language directories (VoicePackUpdateManager.cs:298–319,412–431). For each language it deletes the corresponding target folder recursively if present, recreates it, and recursively copies files; the nominal protected-language name is empty (:29,339–368,435–465). It creates, flushes, and deletes a temporary marker file afterward (:478–499). AudioUpdateHandler.RunAsync only waits for the manager to report completion/error; it is not the operation that starts copying (App/Orqa.TAC.Configurator.Services.Update/AudioUpdateHandler.cs:37–53).

This supports a controller mode exposing writable voice storage. It does not prove the exact USB class/descriptors, storage chip, file format, sound codec, or how storage connects to STM32.

Inferences and unresolved interfaces

  • Strong code-supported inference: TAC has a Nordic-compatible main system firmware/update domain and a separately updated STM32-associated audio domain, plus writable voice-file storage.
  • Not established: exact MCU model/revision, which MCU owns the normal HID/CDC composite device, physical USB mux/hub wiring, Nordic-to-STM communication bus, audio DAC/amplifier wiring, or memory-device model.
  • No evidence in these updater classes establishes IP networking, Ethernet PHY, PoE, RJ45 pinout, MATRIX signaling levels, QS RF control protocol, or RF receiver access.
  • These update transports are distinct from the previously captured normal-mode MAVLink-like heartbeat stream. No code evidence here turns the update commands into a normal operating-mode API.
