TAC 1.3.6 firmware: Ghost serial, STM32 link and cable-length control

Later correlation, 2026-10-11: the user-supplied MATRIX pinout documents C2 contacts 1/2, telemetry 3/6, +50 V/GND 4/5 and CVBS 7/8. Its differential UART 115k note agrees with the firmware's nominal 115200 setting. The offline decoder uses the framing below. These additions do not turn static MCU pin assignments into measured board routing or establish installed firmware identity.

Offline static analysis, 2026-10-11. Input evidence/firmware/nordic/Tac_Ctrl.bin, 291,756 bytes, SHA-256 4c79b25623f07bfc62e8f223e8fbda30b0aba643277d9e13f1fadb6bd15931dd. Firmware addresses below assume the parent analysis's Cortex-M load base 0x27000; a file offset is VA minus 0x27000. No code executed on the controller, no hardware accessed, and no live electrical measurements made.

Result

The firmware contains two distinct hardware UART paths: the Ghost module uses UARTE0 and the STM32-associated internal module uses UARTE1. Both initialize for nominal 115200 baud. Ghost sends framed control/configuration packets; STM32 receives a different framed protocol for audio/control functions. The controller's Cable length setting is sent over the STM32 UART as command 0x04; it does not change the Ghost baud in the traced path.

These are logical MCU interfaces. They do not establish RJ45 pin assignments, line-driver voltage, polarity, isolation, Ethernet compatibility, or which traces reach a physical connector. In particular, the listed GPIO identities are not a wiring instruction.

Reproducible derivation:

  1. ghidra-export/0004c0c0.c builds a zeroed 32-byte config, writes its first words 11,40, baud at offset 0x18 = 0x01d60000, byte at offset 0x1d = 2, and calls 0x3c230. Literal at 0x4c118 is 0x6aac8; callback literal 0x4c11c is Thumb 0x4be5d.
  2. ghidra-export/0005388c.c uses the same layout with words 27,8; literal 0x538e8 = 0x6ac7c, callback 0x538ec = 0x53819.
  3. Async descriptor word 6 points to the driver descriptor: [0x6aac8+0x18]=0x6aab0, [0x6ac7c+0x18]=0x6ac68. Driver descriptor word 3 is its hardware register base: [0x6aab0+0x0c]=0x40002000, [0x6ac68+0x0c]=0x40028000.
  4. 0x3c230 swaps the config's first two words into the lower driver's first two words. 0x3d334 passes those to 0x3c9d0, which writes first argument to MMIO +0x50c (TXD PSEL) and second to +0x514 (RXD PSEL). Thus TX/RX assignment is traced to hardware register writes, not guessed from config field order.
  5. 0x3ca4c writes the configured baud to MMIO +0x524. 0x3ca22 writes zero parity/flow-control configuration to +0x56c for these zero-initialized callers. The receive timeout/config field differs: Ghost 100; STM32 10000. Its exact units are not required for the pin/baud conclusion.

Register meanings checked against Nordic's primary nRF52840 register header and bitfield definitions, retained with hashes under reference/nordic-nrfx-v2.0.0/. TXD/RXD PSEL encode pin in bits 0–4 and port in bit 5. The bitfield header names 0x01D60000 as 115200; exact physical rate depends on clock conditions. This register-map match supports the MCU-family interpretation; this report does not determine package/PCB pad numbering.

Both init functions are connected to application startup: 0x5bea4 directly calls Ghost init; 0x570c8, also called from startup, invokes STM init. These are active code paths in the image, not merely unused driver constants.

Ghost transmit frames, high confidence

ghidra-export/0004c4a0.c builds packets in RAM buffer 0x2000566c and transmits via 0x3c75c(instance=0x6aac8, buffer, length=14):

Byte offset Meaning in the implementation
0 0x81
1 0x0c, counting type + payload + CRC
2 Packet type
3–12 Ten payload bytes
13 CRC-8 over bytes 2–12

The main repeated types are 0x10, 0x11, 0x12. All pack logical control channels 1–4 into four consecutive 12-bit values in bytes 3–8. Types then pack channels 5–8, 9–12, or 13–16 respectively as one byte each in bytes 9–12. Values come through channel resolver 0x521e4; this report does not assign physical stick/button names or aircraft mixer meaning to those channel numbers.

The same function handles types 0x13, 0x21, 0x23 and 0x50..0x56. Type 0x23 forces payload byte 3 to 1. Other packet payload semantics are only established where a producer was independently traced.

0x4c428 is CRC-8 with initial accumulator 0 and polynomial 0xd5, MSB first, no final XOR. Ghidra renders the high-bit step as ~((crc << 1) ^ 0x2a); reduced to eight bits, this is (crc << 1) ^ 0xd5. The known offline check for ASCII 123456789 is 0xbc.

0x4c124 chooses one of the repeated types in rotation when its outgoing queue is empty, handles pending special requests, or sends a queued packet. The queue path uses length byte + 2 for total UART bytes and CRC over type/payload for length byte - 1. It therefore supports variable total frame size, not just the 14-byte RC packets.

Useful literal resolutions: 0x4c7e0→0x2000566c (normal frame), 0x4cb08→0x2000566c, 0x4cb0c→0x2000566e (CRC starts at type), 0x4cb10→0x6aac8 (Ghost UART). Queue frame: 0x4c39c→0x2000fc24, 0x4c3a0→0x2000fc26 (CRC input), 0x4c3a4→0x6aac8.

An example higher-level producer is 0x4d888: it sets packet type 0x50, stores two 32-bit arguments in payload bytes 3–6 and 7–10, clears bytes 11–12, and raises pending flag 5. The parent analysis independently traced this producer from a USB MAVLink SET_HOME command. This proves a particular adapter path, not generic MAVLink tunneling over Ghost.

Ghost receive frames and dispatch, high confidence

Callback address comes from the UART init literal: Thumb pointer 0x4be5d, function 0x4be5c. Its focused decompilation and instruction listing are in ghidra-focused/0004be5c.{c,asm}.

On receive event type 0, the callback marks a connection flag, stops an associated timer through 0x4d860, and processes the received buffer. It has explicit whole-frame branches for 14 bytes and 27 bytes. It validates the last byte against CRC-8 over bytes beginning at offset 2: 11 bytes for the short frame, 24 for the long frame. It also has a limited fragment-assembly path: a chunk starting with 0x80 or 0x90 starts/replaces the temporary assembly; a later chunk is appended and processed if the accumulated total matches 14 or 27.

This is not a demonstrated general stream parser: arbitrary multi-frame concatenation, longer framing and every possible fragmentation pattern have not been proven. The callback even releases the RX buffer before copying/processing in the shown order; no runtime fault claim is made from that alone.

0x4ccc4/0x4cdbc store radio/VTX-associated state and trigger RadPU/RadPD or VTXPwrU/VTXPwrD audio tokens on field changes. 0x4d444 parses two big-endian 32-bit values into state offsets 0x43 and 0x47; those feed the transmission scheduling adjustments in 0x4c124. Detailed units and the full telemetry field map remain open. Recognizing 0x90 as a fragment start does not establish a separate accepted dispatch route; the shown dispatcher only consumes 0x80.

0x4d7cc starts a timer using a state value from 0x200032e2, converted using the expression (value * 32768 + 1000) / 2000. The corresponding receive callback stops it. This is not the UART baud rate and should not be interpreted as cable length. Exact runtime timing depends on the timer API/state; do not infer a live RF packet rate from that expression alone.

STM32/internal serial frames, high confidence

0x538f4 passes bytes directly to 0x3c75c with literal instance 0x6ac7c; wrapper 0x5825c forwards to it. 0x583ac constructs a 16-byte command frame in RAM 0x20014cdc:

Byte offset Meaning
0 0xcc
1 0x0e
2 Command/type argument
3 Value argument
4–14 Remaining shared payload bytes; not all explicitly cleared by this helper
15 CRC-8 over bytes 2–14

CRC routine 0x5840c implements the same polynomial 0xd5, initialized to zero. 0x57124 also builds type 0x02 frames with additional fields/data and sends them through the same UART. Those producers are part of the voice/control subsystem; exact meanings of all payload fields remain unassigned here.

RX callback 0x53818 queues received buffers via 0x5822c; 0x57124 takes the queue, checks CRC and recognizes types 1,3,4,5. A particular type-1 payload beginning 01 01 02 04 sets an additional readiness flag. This code supports communication with an internal STM32-associated device; it does not establish any direct physical connection from this UART to the external ground radio.

Cable length goes to the STM32 path, high confidence

This trace required mapping initialized RAM data as well as code:

  1. Reset function 0x27378 calls byte-copy helper 0x272b6 using literal triple at 0x272e8: flash 0x6daa8 → RAM 0x20003074 through end 0x20003978.
  2. The menu record table at flash 0x6e01c therefore becomes RAM 0x200035e8. Its 33-byte records contain label text, item ID at offset 0x1e, value at 0x1f, and another UI state byte at 0x20. The fourth record begins at flash 0x6e07f and says Cable length; its item ID is 8.
  3. Menu handler ghidra-export/0005ee1c.c follows item ID 8. A press increases the stored byte by 10 until 160, then wraps to 10. The display multiplies that byte by 10 and formats %d m (string 0x6d250, literal at 0x5f864). The UI's range is consequently 100–1600 m in 100 m increments; this is a setting range, not a tested cable capability.
  4. It stores the value at RAM 0x2000fe54+2, invokes 0x58370(value), and saves six config bytes through 0x51f34(0x5000,0x4009,0x2000fe54,6).
  5. 0x58370 queues a command record whose first two bytes are 04 <value> into queue 0x6629c. 0x57124 consumes that same queue (0x573c0=0x6629c) and calls 0x583ac(command,value).
  6. 0x583ac wraps the command in CC 0E 04 <value> ... CRC, sending through 0x5825c → 0x538f4 → UARTE1. Startup 0x570c8 also sends the saved value after STM UART init.

Observed: cable-length selection is conveyed to the STM32-associated module as command 4, and persisted locally. Inference: a second controller subsystem participates in cable-related conditioning/configuration. Unresolved: whether it sets an analog video equalizer, another line-conditioning part, or something else. The STM image/board circuit is needed to resolve its physical effect. No baud-register change, Ghost UART reinitialization or Ethernet/IP configuration appears in this cable-setting path.

Scope limits

The image provides much stronger evidence than product-name strings alone: module source-path strings anchor code, descriptors resolve to actual peripheral MMIO, and packet producers/consumers connect to the UART driver. Nevertheless, function names remain analyst/Ghidra names, not recovered vendor symbols. The analysis assumes the image's established load address and saved decompiler output and distinguishes logical pins from physical connector pins. Current installed firmware/version, signal voltage/polarity, external line transceivers, RJ45 pinout and direct laptop compatibility remain untested.
